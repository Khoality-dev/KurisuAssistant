# CLAUDE.md

Monorepo for KurisuAssistant. The backend and the Android app are independent; the TypeScript clients share one npm workspace:

- `backend/` — Python FastAPI service, WebSocket protocol, Docker Compose stack. Read `backend/CLAUDE.md` before touching it.
- `clients/` — the TypeScript workspace: `packages/` (`models`, `platform`, `api`, `state`, `hooks` — shared, and layered in that order) and `apps/` (one per surface). Read `clients/CLAUDE.md`.
  - `clients/apps/desktop/` — Electron + React + TypeScript client. Read `clients/apps/desktop/CLAUDE.md`.
- `clients/android/` — Kotlin + Jetpack Compose client, not a workspace member. Read `clients/android/CLAUDE.md`.

The backend and Android keep their own toolchain, `.gitignore`, tests and commands, and are run from inside their own directory — the backend in particular uses cwd-relative `data/` paths and `docker compose` must be run from `backend/`. **Speech engines are containers this project does not build** (#212): the backend wraps them over HTTP in `backend/kurisuassistant/speech/`, and each is a published image behind its own Compose profile. The TypeScript clients share one lockfile and one `node_modules` at `clients/`: dependencies install there and nowhere else, so `npm ci` runs at `clients/` even when only one app changed.

Every package's `CLAUDE.md` is an index: a page you can read whole, linking to topic files under that package's `docs/`. Put detail in the topic file and a line in the index, not a fourteenth section in the index.

**There is no user manual, on purpose.** The root `README.md` carries one deployment tutorial — install Docker, three commands, sign in, pick a model — and that is the whole of the user documentation. Anything an operator needs afterwards (backup, restore, updating, removal) is `backend/docs/operations.md`; anything about how the code works is the package's own `docs/`. A nine-page manual was written first and thrown away: wire-protocol numbers and `pg_restore` flags, which the owner correctly called dev documentation. Prose for users is Codex's to write — the split is by audience, not by file type — while the facts it works from, and the check afterwards, are ours.

**Documentation moves with the code.** A change that leaves a document describing what the code used to do is not finished — that is how an architecture map came to point at a screen nothing rendered (#138) and a security section came to present a filed vulnerability as a design decision (#91). Update the package's `docs/` and, for anything cross-cutting, this file, in the same commit.

## Cross-cutting rules

- **Protocol contract** lives in the backend: `backend/docs/websocket.md` and `backend/docs/API.md`, and its machine-readable form is `protocol/events.json`, generated by `backend/scripts/generate_protocol.py` from `websocket/events.py` and `version.py`. Every event name and the wire-protocol integer come from there. **After changing an event or the protocol number, regenerate the manifest and commit it** — `cd backend && python -m scripts.generate_protocol` — then update the clients' own lists (TypeScript: `clients/packages/models/src/events.ts` and `constants.ts`, which every TS app imports; Android: `data/remote/websocket/ProtocolEvents.kt`) and the docs in the same commit. Each package has a test that reads the manifest and fails when its copy drifts, so the three cannot silently disagree the way they did before (#93).
- **Client parity** (QR login payload, storage keys, slash commands, settings) is documented in each client's `CLAUDE.md`. When one client gains a feature the other is expected to mirror, note it in both files.
- **CI** lives in `.github/workflows/` at the root. Each package has a test workflow, scoped by path so a change to one does not run the others: `backend-test.yml` (`backend/**`), `android-test.yml` (`clients/android/**`), `desktop-test.yml` (`clients/apps/desktop/**` and `clients/packages/**`, since a shared package is that app's own code). All three run on `pull_request` and on `push` to `main`. `release.yml` is the one release workflow (#256): a tag `vX.Y.Z` on `main` builds both clients at that version and publishes them under one release with that tag — the NSIS installer, the AppImage and deb, electron-updater's `latest.yml` / `latest-linux.yml`, and the signed APK. There is no backend artifact: the backend is released by the same tag, and a deployment checks it out and rebuilds (`backend/docs/development.md`). One version number: the workflow refuses a tag whose number is not `__version__` in `backend/kurisuassistant/version.py`, and the desktop's `package.json` version and the Android `versionName`/`versionCode` are set from the tag at build time (the committed values are what a local build gets). The desktop's `electron-updater` reads `releases/latest` (`build.publish` in `clients/apps/desktop/package.json`), which is the newest plain release — so the unified release is never a pre-release; the Android `UpdateRepository` lists the releases and `AndroidReleases` takes the newest `vX.Y.Z` that carries an APK. Apps from before #256 look for `android-v*`, so the workflow also publishes the APK as a pre-release `android-vX.Y.Z` until the repository variable `ANDROID_LEGACY_ALIAS` is set to `false`; then that job and the `android-v` branch of `AndroidReleases` go. The former per-client repositories are archived, and `desktop-v*` and `backend-v*` tags are history (the last: `desktop-v0.4.0`, `backend-v0.6.0`); `android-v*` is not yet — the alias job keeps minting `android-vX.Y.Z` pre-releases beside each unified release (the last hand-made one was `android-v0.3.0`) until `ANDROID_LEGACY_ALIAS` is `false`. Signing needs two secrets, `KURISU_KEYSTORE_BASE64` and `KURISU_KEYSTORE_PASSWORD`; the desktop build needs none. There is no long-lived `dev` branch; `main` is the only line of development, and a deployment is a separate checkout of a tag — never the tree you develop in, because the two would share `backend/data/` and the fixed Compose project name. The code itself is in the image (the Dockerfile copies it), so the rebuild is what ships a change, and only the dev overlay mounts source over it. Where checkouts live and how they are proxied varies per developer and is not documented here.
- **Run the tests locally too**, since path filters mean a cross-package change only triggers some of them: `pytest -m "not integration"` from `backend/` (the model is always the in-process mock Ollama in `tests/mock_ollama`; `db`-marked migration and system tests need Postgres and skip without one — CI provides it; `integration` means a live model, run by hand only because it costs money), `npm test` from `clients/` (it runs every workspace member, including the boundary test that keeps the shared packages shareable), `./gradlew :app:testDevDebugUnitTest` from `clients/android/`. The Android instrumented suite (`connectedDevDebugAndroidTest`) needs an emulator and the standalone mock backend from `clients/apps/desktop/` (`npm run mock:backend -- --host 0.0.0.0`): every client test — unit, e2e, instrumented, screenshot capture — runs against that mock and never a deployed backend, and when mock and backend disagree the backend wins and the mock is fixed in the same PR (#126). The desktop Playwright e2e drives real Electron and needs a display — CI runs it under `xvfb-run` on Linux, and on a headless machine use `npm run test:e2e:docker` (see `clients/apps/desktop/CLAUDE.md`), which needs nothing installed but Docker.
