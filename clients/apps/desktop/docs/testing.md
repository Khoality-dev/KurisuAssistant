# Testing

[← clients/desktop](../CLAUDE.md)

What runs where, and the one suite that cannot run on the host.

E2E tests live in `tests/` and run via Playwright's Electron support.

- `playwright.config.ts` — serial, single worker (each test spawns its own Electron + mock backend).
- `tests/fixtures.ts` — `test` fixture that launches Electron pointing at `dist-electron/main.js` with an isolated userData dir (via `KURISU_E2E_USER_DATA_DIR` env var, which `electron/main.ts` honors for tests only), starts a mock backend on a random port, and seeds `kurisu_backend_url` in localStorage before reload. The `appPaths` fixture owns that temp dir, the path of the main process's `settings.json` inside it, and a free port passed as `KURISU_E2E_MCP_PORT` — the built-in MCP server must not be tested on its default port, or the suite would be driving whatever install is already running on the machine.
- `tests/mock/server.ts` — HTTP + WebSocket mock. Endpoints: `/version`, `/login`, `/register`, `/auth/refresh`, `/users/me` (+ tool-policies), `GET|PATCH /assistant`, `GET|POST /personas` and `GET|PATCH|DELETE /personas/{id}` (+ `/enabled`), `GET|POST /sub-agents` and `GET|PATCH|DELETE /sub-agents/{id}` (+ `/enabled`), `GET /conversations` (honours `?persona_id=`, and answers it with the same stingy one-element shape the backend does), `GET|PATCH|DELETE /conversations/{id}`, `/models`, `/tools`, `/mcp-servers`, `/skills`, `/faces`, `/tts/*`, the Kurisu Drive routes (`/drive/nodes`, `/drive/resolve`, `/drive/folders`, `/drive/files` incl. a small multipart reader, `/drive/files/{id}/content`, `/drive/usage`), `GET /character-assets/{persona}/{pose}/{file}` (the first route here to insist on a bearer, because that is what `characterWindow.spec.ts` is about; only the base image of a pose the persona has answers a PNG, anything else is a 404), the 3D character store (#236: `PATCH /character-assets/{id}/character-config` with the backend's merge and server-owned `vrm.model`/`vrm.clips`, `PUT|GET|DELETE …/vrm/model`, `PUT …/vrma`, `GET|PATCH|DELETE …/vrma/{clip_id}`, `GET /character-assets/usage` — uploads are checked for their `?sha256=`, the per-file ceilings, the quota and the same `415` codes as the backend through `tests/mock/vrmFixture.ts`; every one of these wants a bearer and honours `expireAccessToken()`, as the backend's do; uploads are refused in the backend's order (quota, then size, then digest and format), and the two GETs answer `ETag`/`304`/`nosniff`; any other `/character-assets` path is a 404, never the `{}` below), plus `/ws/chat`. There is no `/agents`: it falls through to the catch-all `{}`. `refuseLikeAProxy(status)` makes the whole mock answer like a proxy with its own error page (#263).
  **That catch-all is a trap.** It answers `{}` with a **200**, so a route the mock has not implemented looks like empty data rather than a missing endpoint — new routes go above it, and `tests/mock/server.test.ts` asserts a missing drive path is a 404.
  The drive is seeded by path (`new MockBackend({ drive: [{ path: '/Reports/Q3.md', content: '# Q3' }] })` or `addDriveEntry`), which builds the folders it implies; `getDrivePaths()` and `lastDriveUpload` read it back. `driveQuotaBytes` drives the 507. It authenticates nobody, so **who may read whose files is not testable here** — that lives in the backend's `db` suite.
  Over the socket it emits `connected` (with `persona_id`), `stream_chunk`, `done`, and — on a `compact_context` event — `context_info` twice, compacting the conversation in place the way the server does (#99). It enforces the wire protocol in the handshake, closing with 4426 on a mismatch.
  Configurable via `setStream`, `setTools`, `setAssistantModel` (pass `null` for a fresh account that has never had one chosen), `addPersona`, `addSubAgent`, `addMcpServer`, `setWireProtocol(n)` (what `/version` reports, what every other request's `X-Wire-Protocol` is checked against for a 426 with the backend's body shape, and what the socket handshake closes 4426 against), `setBackendVersion(v)` (the `backend_version` in the same two places; by default it is the desktop `package.json`'s own version, so a build and its mock are one release and Settings → Account shows no mismatch unless a spec asks for one, #257) and `setUnreachable('/tts/models' | '/models')` (answer 502 as the backend does when the service behind the endpoint is down). `dropAllWebSockets()` simulates a silent backend socket loss. `setCharacterConfig(personaId, config)` gives a persona a character (`ONE_POSE_CHARACTER` is the smallest one; `VRM_CHARACTER_WITH_MODEL` is persona 1 with the fixture model uploaded, served without an upload). The fixture (`tests/mock/vrmFixture.ts`) builds the smallest VRM 1.0 model and VRMA clip **in code** with their sha256 — not a file read, because the standalone mock is bundled into `dist-mock/` where a path next to the module finds nothing. `characterQuotaBytes` lowers the store's quota for a 507. `expireAccessToken()` makes the character-asset routes — and only they — refuse the login's bearer with a 401 while `/auth/refresh` keeps issuing `test-access-token-refreshed`. Tracks `lastChatRequest`, `lastConversationPatch`, `lastMcpServerCreate`, `lastCharacterAssetRequest` (path and Authorization header) and `characterAssetRequests` (every asset GET with the status it got) for assertions; `getConversation`/`getConversations`/`getPersonas`/`getAssistant` read its state back.
  A scripted `StreamChunk` speaks as the conversation's bound persona unless it sets `personaId`/`personaName` — which is how a handoff is scripted, since the client splits assistant bubbles on `persona_id`. A `role: 'tool'` chunk carries `name`, `toolKind` and `durationMs` instead, and goes out with `persona_id`/`persona_name` null.
- Specs (Playwright, `*.spec.ts`): `smoke.spec.ts`, `streaming.spec.ts`, `settings.spec.ts`, `mcp.spec.ts`, `resilience.spec.ts`, `regression.spec.ts`, `mcpServer.spec.ts`, `credentials.spec.ts`, `firstRun.spec.ts`, `updateRequired.spec.ts`, `unreachableServices.spec.ts`, `drive.spec.ts`, `characterWindow.spec.ts`, `loginFailures.spec.ts`, and the manual `vrmRender.gpu.spec.ts`.
  - `characterWindow.spec.ts` opens the character window from the chat header's Face icon, sends a message so the persona is pushed to it, and asserts the window's fetch of the persona's base image carried the session's bearer and got a 200 from the mock, and that logging out closes the window. The keychain check forks on `credentials.isSecure()` like `credentials.spec.ts`: with a keychain (Windows CI, a desktop with a secret service) the login's "Remember me" — on by default — writes the pair, and the spec pins that the file is byte-identical after the window has fetched, which a window-side `setToken` would break by storing a null refresh token; without one (the Linux CI container) nothing is ever written, and it pins only that the window did not make a file appear — the memory-only adoption itself is pinned by `storage.test.ts`. A second test ages the login's token out of the mock's asset route (`mock.expireAccessToken()`) before the window opens and asserts the round trip: a 401 in the window, a refresh through the main window, a retry carrying `test-access-token-refreshed` that gets a 200. It attaches its own console listeners to the second window — the fixtures only listen to the first. No WebGL, no pixels: the 2D canvas is not asserted on (#237).
  - `loginFailures.spec.ts` puts the mock in front of the app as a proxy would be — `mock.refuseLikeAProxy(403)` answers every request, `/version` included, with an nginx-style HTML page and no `detail` — and asserts the login screen's sentence names something in front of the server, never "Request failed with status code 403"; a second case does the same for a 502 (#263). `mock.refuseLikeAProxy(null)` restores the mock.
  - `drive.spec.ts` walks Kurisu Drive in the running app: two roots in one explorer, the drive's own listing, opening a file with the server's bytes, the quota bar, creating a folder that reaches the mock, the transfer tray, and the Settings policy. The unit tests pin `fileSource`'s routing against stubs; this pins that the explorer actually shows it.
  - `updateRequired.spec.ts` sets the mock's wire protocol away from the client's before boot and asserts the gate says which side to update and that "Change server" lands on the login form; then logs in on a matching protocol, moves the mock's, and asserts the next 426 raises the same screen (#150).
  - `unreachableServices.spec.ts` makes `/tts/models` and `/models` answer 502 and asserts the settings screens show the server's reason instead of an invented or empty list (#151).
  - Every spec's `send()` helper fills the composer and clicks Send straight away, on purpose: that is the race in #145 (the composer used to wipe a draft when its persona or conversation resolved after login, which on a slow runner happened after the fill). The fix is in `ChatComposer`, pinned by `src/components/chat/ChatComposer.test.tsx`; the helpers stay naive so the e2e keeps exercising it.
  - `firstRun.spec.ts` puts the mock in the state a brand-new account is in — `mock.setAssistantModel(null)` — and asserts the first message gets the `NoModelPrompt` and its way onto the Assistant screen rather than the red toast, that the refused text comes back to the composer, and that choosing a model lets the same message through (#149).
  - `mcpServer.spec.ts` drives the built-in MCP server over HTTP — token minted, anonymous refused, browser refused, SSE stream opens, nothing reachable off loopback. It talks to the app other than through the UI, and it earned that: the header heuristic in `mcpServerAuth.ts` passed every unit test while refusing every real client, because Node's `fetch` sends `sec-fetch-mode`.
  - `credentials.spec.ts` logs in and checks that no token reaches localStorage, then forks on `credentials.isSecure()`: with a keychain the session survives a reload and the stored file holds no readable token; without one (a CI container has no secret service) nothing is written and the reload lands back on the login form.
  - `vrmRender.gpu.spec.ts` (#240) is tagged `@gpu` and **excluded unless `KURISU_E2E_GPU` is set** (`grepInvert` in `playwright.config.ts`): it loads a real VRoid export (`KURISU_VRM_FILE`, served to the character window by route interception) and asserts the stage reached `data-status="ready"` and drew more than a handful of distinct colours (`readPixels` inside a frame). CI never runs it — nothing there has a GPU, and `KURISU_E2E_ELECTRON_ARGS`, the fixtures' only way to add GPU flags, is unset — because launching the app differently from how it ships would prove the wrong thing.

**Manual GPU checklist** (a VRM change, before merge; CI cannot answer any of these). On a machine with hardware graphics, against a real backend and a real VRoid export:

1. The packaged app (not `npm run dev`) loads the model in the character window under the packaged CSP; the window shows "Loading 3D model" with a moving "x of y MB" first.
2. Close and reopen the window: the model request answers 304 (backend log or DevTools), and the stage is back without the byte counter crawling again.
3. Four VRM personas in one conversation: one live stage, three "waiting" cards; switching who speaks moves the stage and never fails with a lost context.
4. A 2D persona beside a VRM one: both draw.
5. Pull the network cable mid-download: "Couldn't load …" with the download sentence; reconnect, and it loads without a click.
6. `KURISU_E2E_GPU=1 KURISU_VRM_FILE=… KURISU_E2E_ELECTRON_ARGS="--use-angle=swiftshader --enable-unsafe-swiftshader" npx playwright test tests/vrmRender.gpu.spec.ts` passes.
7. A screenshot of the live stage goes in the PR body.

- Unit tests (vitest, `*.test.ts`) run with no Electron build. Under `apps/desktop`: `tests/mock/server.test.ts` pins the mock's own shapes against the backend contract (including the asset route's 401 for an expired bearer and its acceptance of the refreshed one), `tests/mock/cli.test.ts` pins the standalone entry's argument parsing and starts every scenario once, `tests/appTools.test.ts` fails the build if an app tool is advertised without a handler, `tests/hostToolPolicy.test.ts` / `tests/mcpConsent.test.ts` / `tests/mcpServerAuth.test.ts` cover the three security decisions the main process makes — which paths a host tool may touch, which programs may be spawned, who may reach the built-in MCP server — and `tests/webSecurity.test.ts` pins the packaged CSP. The rest moved with the code into the shared packages (run from `clients/`, #225): `packages/api/src/storage.test.ts` pins the negative property that no token is ever written to localStorage, and that every change of the access token is pushed to the character window while the refresh token never is (#237); `packages/api/src/characterUploads.test.ts` that a model upload carries the body's sha256 and no timeout and that every refusal becomes a `CharacterUploadError` with the server's code (#236); `packages/api/src/authedFetch.test.ts` the single 401 retry, that the bearer goes to the backend's origin and to no other host, that a root-relative path is fetched from the backend rather than the page (#298), and the byte progress a model download reports (a body short of its `Content-Length` is an interrupted download); `packages/ui/src/character/CharacterSurface.test.tsx` and `CharacterStack.test.tsx` each VRM state's wording, that a display without WebGL never imports the engine, and that three VRM personas make one driver and two cards (#240); `packages/api/src/fileSource.test.ts` the two-roots seam — which paths go to the server, the node-id cache, and the separator arithmetic on a simulated win32 platform; `packages/api/src/wireProtocol.test.ts` the update screen's copy; `packages/state/src/conversationStore.test.ts` and `packages/state/src/commands.test.ts` the conversation store and the slash-command parser (including that `/live-animate` answers rather than dispatches on a host with no character window); `packages/state/src/transferStore.test.ts` the transfer lifecycle against a stubbed bridge; `packages/hooks/src/characterSession.test.ts` that the window's `ready` is answered with the session before the personas (the pure function's order — the hook wiring is covered by the e2e, since `hooks` may not render); and `packages/ui/src/components/chat/ChatComposer.test.tsx` renders the composer (react-dom + `act`, no testing-library) and pins that a draft survives its scope resolving and is dropped when leaving a conversation. `vitest.config.ts` includes `tests/**/*.test.ts` alongside `src/**`; the `.spec.ts` / `.test.ts` split is what keeps the two runners apart.
## The standalone mock

`npm run mock:backend -- --port 15597 [--host 0.0.0.0] [--scenario <name>]` starts the same
`MockBackend` on its own and keeps it running until Ctrl-C (#126). `tests/mock/cli.ts` is the
entry; `package.json` bundles it with esbuild into the gitignored `dist-mock/` first, so a checkout
needs `npm ci` and nothing else. Any username and password sign in. `--host 0.0.0.0` is for an
Android emulator, which reaches the host at `http://10.0.2.2:<port>`, or for a phone on the LAN.
`MOCK_DEBUG=1` logs every socket event.

Scenarios (`tests/mock/scenarios.ts`, `--list` prints them) are the states the specs script by
hand, so what you see driving a client is what the suite asserts on — keep them in step with the
specs:

| Scenario | State |
| --- | --- |
| `default` | Two personas (Kurisu answers, Amadeus available), a model chosen, a short streamed reply |
| `docs` | The cast the Android documentation screenshots are taken from: personas, assistant and memory, sub-agents, MCP servers, tools, skills, and four seeded conversations of different ages, one with a tool rail (#194, #195) |
| `tool-call` | Assistant text interrupted by a `lookup` tool result, then the answer |
| `sub-agent` | A step delegated to a sub-agent mid-answer — the `sub-agent` tag and duration |
| `handoff` | Kurisu starts the answer, Amadeus finishes it: two bubbles, two speakers |
| `thinking` | A thinking chunk before the answer (the collapsible "Thinking" block) |
| `slow` | One chunk every 400 ms for a while — long enough to press Stop |
| `character` | Kurisu has a one-pose character, so the character window has art to fetch — with a bearer, as on the backend |
| `vrm` | Kurisu is a VRM persona with the fixture model already uploaded, so the model GET answers bytes with an `ETag` and a `304`, and the upload routes have something to replace (#236) |
| `no-model` | A fresh account with no model chosen: the first message is refused with `NO_MODEL_SELECTED` |
| `emotion` | Kurisu is a VRM persona with the emotion channel on: the reply's chunks carry `emotion` / `emotion_at` and the stored message keeps `emotion_cues` (#243); nothing renders them until #244 |

The mock has no tool-approval flow: nothing in the client is driven by `tool_approval_request` from
here yet, and adding it means adding it to the mock first.

**Client tests — unit, e2e, instrumented, screenshot capture — run against the mock backend, never against a deployed one. The mock mirrors `backend/kurisuassistant/`; when the two disagree, the backend wins and the mock is fixed in the same PR as the protocol change.**

Commands: `npm test` (vitest, no build needed), and `npm run test:e2e:build` (vite build → `dist/` + `dist-electron/`) then `npm run test:e2e` (or `test:e2e:headed` for debugging).

**On a headless machine, run the e2e in Docker: `npm run test:e2e:build` then `npm run test:e2e:docker`.** Playwright drives real Electron, which cannot start without a display, so `npm run test:e2e` fails on a server or a container with no X — and installing `xvfb` needs root. The `mcr.microsoft.com/playwright` image ships both Xvfb and the GUI libraries, so the Docker route needs nothing but Docker. It mounts the package, runs as the calling uid so build artefacts stay owned by you, and sets `HOME=/tmp` and `--shm-size=1g` because Chromium needs a writable home and more than the default 64 MB of shared memory. **The image tag is pinned to the `@playwright/test` version (currently `v1.63.0-noble`) and must be bumped with it** — a mismatch fails with a browser-not-found error that reads like a missing install.

It invokes `./node_modules/.bin/playwright` rather than `npx playwright`, deliberately. `npx` with no TTY and closed stdin — which is what `docker run` gives it under `npm run` — blocks on its install prompt forever: Xvfb comes up, no node process ever starts, and the container sits there looking like a slow test run rather than a hang.

This is not a nicety: the e2e suite is the only one that cannot run on the host, and a WebSocket reconnect regression reached CI precisely because it was the suite nobody could run locally.
