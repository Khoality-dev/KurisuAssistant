# Character animation

[← clients/desktop](../CLAUDE.md)

The character: the feed every surface reads, the driver seam every kind of character sits behind, the two surfaces that show it — inline in the chat column and a second window — the 2D engine, and the editor that produces the configuration.

**The live feed is a store, not a wire** (#238). Everything a character reacts to is written into `@kurisu/state`'s `characterFeedStore` by its producer and read from there by whatever surface is showing: `useTTS` publishes one `SpeechSegment` per spoken sentence (the sentence's RMS curve, its own window length, and `startedAt` stamped on the audio element's `playing` event — never on the call to `play()`) plus a `SpeechSync` every 500 ms from `audio.currentTime`, and `null` when the queue drains; `useStreamingChat` sets `thinking` and, with speech off, pushes a feeling to show (`pushEmotion`, below); `visionStore` pushes gesture bursts (each with a rising `seq`, so a surface takes a burst once and two surfaces cannot steal each other's) and sets the faces in view; `useCharacterPanel` keeps the personas in the conversation and who is speaking (the reactive half, zustand), publishes subtitle events, and pushes the feeling a reopened conversation rests on. Nothing is sampled at frame rate in the producer: a surface's own loop calls `sampleSpeech` (`@kurisu/models` `speechClock.ts`) against the segment and the last sync, interpolating the curve and slewing toward the sync at most 20 ms a frame — so hiding the main window to the tray, which throttles its timers, no longer stalls the mouth, and a phone's output latency is absorbed by the first sync. `resetCharacterFeed()` is silence.

**One driver contract, any surface.** `CharacterDriver` (`@kurisu/models` `characterDriver.ts`: `load`, `update(dtMs, DriverInput)`, `resize`, `dispose`) is what a surface holds; `CharacterSurface` (`@kurisu/ui/src/character/`) owns the box, a `ResizeObserver`, and the frame loop that samples the feed and calls `update`, and picks the driver by `character.kind`. Two drivers exist: `PoseGraphDriver` — an adapter over the unchanged `CanvasCompositor` (the compositor keeps its own render loop; the adapter writes its three input fields, forwards gestures and faces, serialises loads so a newer one supersedes an older, turns a config it cannot draw into a readable rejection, and makes `dispose` idempotent) — and `@kurisu/vrm`'s `createVrmDriver` for a VRM persona (#240, below). The conformance cases in `@kurisu/vrm/testing` run over the adapter (`PoseGraphDriver.test.ts`), and `CanvasCompositor.test.ts` pins the engine's own behaviour with a recording context and a hand-stepped loop. A persona's character is reloaded when `characterFingerprint` (`@kurisu/models`) changes — the tree's content, or a VRM's model/clip digests and settings — not on object identity and not on counts, which is what let an image edit go unnoticed before.

**Inline, in the chat column** (#241). The Face icon on the chat header and `/live-animate` both dispatch `kurisu:toggle-character`, on every host, and show or hide `CharacterPanel` above the messages: the same `CharacterStack` the window draws (side by side here, since the column is wider than tall), from the same feed store, with the same `SubtitleQueue` fed by the feed's subtitle events. It is the only character surface a browser has. `layoutStore` remembers whether it shows and its height (see [architecture](architecture.md)); a vertical `ResizeHandle` under it drags between 160 px and three fifths of the column.

**Popped out, into a separate Electron window.** Where `capabilities.characterWindow` is true the panel's top-right corner carries "Pop out character"; while the character is out the panel draws nothing and says "Showing in its own window" with "Pop in character" — one stage per persona at a time, never live in both (`ChatPanel` sets `inlineVisible` only while the panel draws). `ChatPanel` is the one owner of that state: `windowOpen` flips before `open()` resolves, so the feed to the window is on before the window can ask for it; `onWindowClosed` flips it back, which brings the character back inline; a `ready` from the window flips it on — which is what re-syncs a main renderer whose idea of the window is stale; and hiding the character while it is out closes the window. (Nothing opened the window at all between the layout rewrite and #237; the docs said "Face icon in top bar" about a button that no longer existed.) **A reload of the main renderer closes the window** (`did-start-navigation` in `electron/main.ts`): the reloaded renderer would otherwise start with no memory of a window that lives on holding a token nobody refreshes; the next toggle opens a fresh one. The window opens as an independent, resizable (aspect-ratio-locked 2:3) frameless BrowserWindow — same Vite bundle routed via `?window=character` query param → `CharacterWindowApp` (no login and no stores of its own, purely IPC-driven). Default 512×768, min 256×384.

**It has no session of its own.** The asset routes are bearer-only, and a second renderer has its own empty copy of `storage`'s token memory, so the main renderer pushes the access token over `character:session` (below) and the window fetches nothing until the first push has arrived — even one saying there is no session. A null push clears its image cache and shows "Signed out"; `authStore.logout` pushes null and closes the window.

**A VRM persona in the window** (#240). `CharacterSurface` draws one with `@kurisu/vrm`, and reaches the engine only by `import('@kurisu/vrm')` — never by a static specifier of the package or any subpath but `/probe`, bare side-effect imports included (a `boundaries.test.ts` case pins it), so three.js stays out of the main window's chunk and the browser build for a 2D-only user. Before the import it asks `supportsWebGL` (`@kurisu/vrm/probe`, engine-free) for a WebGL 2 context — three.js 0.186 has no WebGL 1 renderer — on a throwaway canvas it releases at once with `WEBGL_lose_context`, never the stage's own (a context is pinned to the canvas that first asked, with that request's attributes, so probing the stage would hand the renderer the probe's context); a display that says no gets "A 3D character needs hardware graphics on this display" and the chunk is never fetched — which is also what keeps the surface mountable under happy-dom, whose `getContext` is always null. The canvas is keyed by kind, because a 2D context and a WebGL one cannot share an element, and the VRM driver is made with `releaseContextOnDispose` since its canvas leaves the document with it. Asset URLs in the config are root-relative (`/character-assets/{id}/vrm/model`); `fetchAuthedBytes` places such a path on the backend (`onBackend`), since the packaged page's own origin is `file://`. It is done there, not by each caller, because the 3D setup's preview once handed the path over bare and failed with "Failed to fetch" after every upload (#298). What the surface shows for a VRM persona, by `data-status` on the box:

- **no-model** — `vrm.model` is null: "No 3D model yet" and "Upload one in Settings → Personas → {name} → Set up 3D character." No driver, no engine.
- **loading** — "Loading 3D model", a bar, and "12.1 of 18.4 MB": `fetchAuthedBytes(url, init, onProgress)` reads the model's body chunk by chunk (the clips are fetched without progress), reported at most every 100 ms; the total is `Content-Length`, else `vrm.model.bytes`. A body shorter than its `Content-Length` is a `DownloadInterruptedError`, not a corrupt model.
- **failed** — "Couldn't load {vrm.model.filename, else 'the 3D model'}", then: the loader's own words for a `VrmLoadError` (matched by name, so the class is not imported into the main chunk); "The server has no file for this model any more…" for a 404 (`AssetRequestError.status`); "The download stopped before the whole file arrived. The window tries again when the connection comes back." only for a failure of the connection itself (`fetch` rejecting with a `TypeError`, or a `DownloadInterruptedError`); and "Something went wrong loading the 3D model." for anything else — a 401/403/5xx, an engine chunk that would not import (a stale chunk after a redeploy), a renderer that would not start. It retries on "Try again", on the window's `online` event, and on the next session that carries a token; when what failed was making the driver (the chunk or the renderer), those same paths make it again rather than re-running a load that has no driver.
- **nogl** — the sentence above.
- **ready** — the stage on `vrm.camera.background`.

**At most one 3D stage per window.** `CharacterStack` (`@kurisu/ui/src/character/`) renders the personas in the conversation, and among the VRM personas that have a model exactly one gets a live `CharacterSurface`: the active persona, else the VRM persona that spoke last, else the first (`liveStagePersona`). Every other one is a card — its avatar (`useAuthedAssetUrl` on `/images/{uuid}`, header-authenticated), its name, "waiting" — until it speaks. 2D personas are not counted and keep drawing beside it; a VRM persona without a model shows its notice and needs no stage. The reason is Chromium's cap of about sixteen WebGL contexts and what software GL can hold, not taste. The whole window is a drag region; a VRM box opts out (`WebkitAppRegion: 'no-drag'`) so it receives pointer events, and a 24 px strip along the window's top keeps it movable. The 2D path keeps its 2:3 window and fixed 400×600 backing store; the VRM stage sizes itself from the box.

**IPC channels** (every one relayed by the main process, which inspects none of them; the direction is given per channel). The window is a second renderer with its own copy of the feed store: the main renderer's `useCharacterBridgeSync` (mounted in `ChatPanel`, the owner of the open/closed state) mirrors every feed write over these channels while `windowOpen` is set, and the window writes each message into its store, from which its `CharacterSurface`s read exactly as an inline panel would (#241). Nothing crosses at frame rate.
- `character:ready` — character window → main renderer, once the window's listeners are subscribed. Answered with `character:session`, then `character:personas-update`, then what the feed holds right now (`character:feed` — with a feeling that still holds —, `character:face-update`, `character:speech`, and a `character:speech-sync` if one is pending) so a window opened mid-sentence catches up. The main renderer's handlers for this and for `character:session-request` are subscribed regardless of what it believes about the window, because a `ready` is proof the window exists — and a `ready` sets `windowOpen`.
- `character:speech` — main renderer → character window: a `SpeechSegment` when a sentence's audio begins, `null` when speech ends. One message per sentence.
- `character:speech-sync` — main renderer → character window: `{ positionMs, at }`, the producer's real playback position, every 500 ms while a sentence plays.
- `character:feed` — main renderer → character window: `{ isThinking }` on change, and `{ isThinking, emotion: { cue, personaId, at } }` for a feeling shown outside speech (#244). The window pushes it into its own store with the main renderer's `at`, so a hold is measured from when it was shown there; the `ready` catch-up includes it only while it still holds.
- `character:personas-update` — main renderer → character window: `{ personas: [{id, name, avatarUuid, character}], activePersonaId }` on persona map or active persona change; `character` is the parsed config, whatever its kind
- `character:gesture-update` — main renderer → character window: `{ gestures: string[], seq }`, one burst from the vision pipeline
- `character:face-update` — main renderer → character window: `{ faces: string[] }`, the identities currently in view, level state for `face` conditions
- `character:subtitle` — `{ text: string, isUser: boolean, duration?: number }` subtitles displayed as overlay at bottom of character window, by `SubtitleQueue` (`@kurisu/ui/src/character/subtitleQueue.ts`, a pure module the inline panel will share). Assistant text: `sentenceDuration = chunkDuration / sentenceCount` (chunk split on `.!?。！？\n`). TTS success → chunkDuration = WAV duration; TTS error → chunkDuration = 4s. Sentences queued and shown sequentially, chaining immediately, fade only after last. User text shown immediately with word-count-based hold. Empty text clears (cancel).
- `character:session` — `{ accessToken }` main renderer → character window, sent from `storage.setToken`, `clearToken` and `clearTokens` (so a login, a refresh and a sign-out all reach it) and first thing on `character:ready`, **before** `character:personas-update`. Only ever the access token — never the refresh token. The window takes it with `storage.adoptToken`, never `setToken`: `persistTokens` writes both fields from that window's memory, and a window holding no refresh token would null the persisted one.
- `character:session-request` — character window → main renderer: an asset fetch came back 401. The main renderer refreshes (which re-pushes through `storage.setToken`) or, with nothing to refresh, re-sends what it holds so the window's wait ends. `fetchAuthedBlob`/`fetchAuthedBytes` in `@kurisu/api` is the one authenticated fetch on both sides — the image cache, the compositor's videos and `useAuthedAssetUrl` all go through it — and retries exactly once with whatever the renderer's configured refresher returns (`apiClient.tryRefresh` in the main window, the request round trip in the character window). **It sends the bearer to the backend's origin only**: a pose tree may carry an absolute URL, and a foreign host is fetched plain, with no retry on its 401. The window waits at most 10 s (`SESSION_REQUEST_TIMEOUT_MS` in `CharacterWindowApp.tsx`) for the next `character:session`; on expiry the retry is skipped, the 401 stands, and the asset is reported as failed to load — the window does not sign out. A load that failed is retried once the next session carrying a token arrives (`CharacterSurface`'s `retryToken`); a load that succeeded ignores a routine refresh.
- `character:window-closed` — main process → main renderer when user closes character window
- `character:open-window` / `character:close-window` — renderer invokes main process to create/destroy window

**The Android page** (#245). Android hosts the same renderer in a WebView instead of growing a second one (#246), and its build has no JavaScript toolchain, so the page is a **committed build artifact**: `clients/android/app/src/main/assets/character/index.html`, one self-contained file built from `@kurisu/vrm` alone (`src/page/index.html` + `main.ts`) by `npm run build:page -w @kurisu/vrm` from `clients/`. `vite.page.config.ts` inlines the one script chunk and the styles into the HTML and puts a `Content-Security-Policy` `<meta>` right after the charset that names that script by its sha256 — `default-src 'none'`; `connect-src 'self' blob: data:` (the model and clips from the page's own origin, and GLTFLoader's texture blobs, which it *fetches*); `img-src blob: data:`; no workers, frames, base or forms — so the file is safe in a host with no request interceptor too. Never edit it by hand: `.gitattributes` marks it `binary` (a line-ending rewrite would break the hash) and the `checks` job in `desktop-test.yml` rebuilds it and fails on any difference. The page is `CharacterSurface` without React or the store: `page/runtime.ts` keeps the latest of each message as the feed, loads a VRM config's model through a same-origin `fetch` of its root-relative URLs **verbatim** (the host answers `/character-assets/` itself and keeps the token), reconfigures without reloading when only settings change, and samples the feed into the driver once a frame — `sampleSpeech` on `Date.now()`, a sentence's cue fired once when the audio passes its `delayMs`, a gesture burst taken once per `seq`, and the `resting` emotion applied as the driver's `default_expression`. In: `window.__kurisu.push(message)` (what `evaluateJavascript` calls) or a `MessagePort` handed over once as `postMessage('kurisu:port', [port])`; the messages are `page/host.ts`'s, one golden fixture each under `page/fixtures/`, which the Android JVM tests decode too. Out: `KurisuNative.ready()`, `firstFrame()` and `error(code, message)` (`code` is `nogl`, `load` or `message`) when the host installed that interface, else the same events as JSON over the port. `document.documentElement.dataset.status` says `idle`, `loading`, `ready`, `failed`, `no-model` or `nogl`, as `CharacterSurface`'s box does. The desktop surface does not apply segment cues or the resting emotion yet (#244); when it does, the page's rules are the ones to share.

**Canvas compositing**: Base image + diff patches (eyes, mouth) at stored positions. Blink: configurable random interval state machine (default 2-6s). Breathing: sine wave vertical offset (configurable amplitude/period). Lip sync: audio amplitude → mouth patch index. Per-persona character configs stored in backend DB as JSON. **State machine**: IDLE (blink/breathing/mouth + event listening) → TRANSITIONING (playing edge video on canvas, all events ignored) → IDLE (switch to target pose, apply node settings, reset timers). During transitions no events are processed; random timers start fresh when arriving at a node. **Multi-transition edges**: Each directed edge (`AnimationEdge`) contains `transitions: EdgeTransition[]` — multiple transitions per edge, each with its own condition, video list, and playback rate. One edge per directed node pair (ID: `{source}-{target}`). Timer keys use `${edge.id}:${transitionIndex}`. Legacy edges (single condition/video_urls/playback_rate) auto-migrated on load via `migrateEdgeToTransitions()`. Legacy IDs (`pose-*`/`edge-*`) auto-migrated to 8-char random hex via `migratePoseTreeIds()` (calls `POST /character-assets/{persona_id}/migrate-ids` to rename files on disk). Bidirectional edges render side-by-side with perpendicular offset (not overlapping). Transition conditions: `random` (timer-based), `thinking` (fires when `isThinking` matches `condition.value`), `gesture` (fires when a detected gesture matches `condition.value`, e.g. "wave", "thumbs_up", "peace_sign"), `face` (fires while the named identity is, or is not, in view). `isThinking` and faces are live variables observed each frame while idle — no edge detection; a gesture is consumed by the tick that sees it. **Transitions are evaluated in edge order and the first whose conditions all hold wins** — never a random choice among matches — and an instant (video-less) transition returns to idle synchronously, so a level-triggered edge can chain several hops inside one frame (`CanvasCompositor.test.ts` pins both). **Per-node animation settings**: `AnimationNode.animation_settings` (optional) configures breathing (enabled/amplitude/period) and blink timing (min/max interval, close/hold/open duration). Applied via `applySettings()` on each pose switch. UI: sliders in PoseNodeEditor Preview step.

**Asset pipeline**: AI-generated base → inpainted variants → backend OpenCV diff → cropped patch PNGs. Assets stored in folder structure: `data/character_assets/{persona_id}/{pose_id}/base.png`, `{part}_{index}.png`; videos in `{persona_id}/edges/{edge_id}.mp4|.webm`. Re-uploading overwrites without changing URLs. Orphaned assets cleaned up on config save.

**Config shape** (`@kurisu/models` `character.ts`, wire protocol 7, #235): `character_config` is `{ kind: 'pose_graph' | 'vrm', pose_tree?, vrm? }` — `kind` selects what renders and the two members coexist, so switching back needs no upload. `parseCharacterConfig()` is the one reader (`{ kind, poseTree, vrm }`, null for anything without a recognised `kind`; there is no kind-less fallback, the backend stamps every row). A save is a merge per member: the graph editor sends `{ kind, pose_tree }` with the kind it loaded and never touches `vrm`; a member left out is kept server-side, `null` clears it. Both render in the window (#240); the settings card says what the persona has ("3D model · kurisu_v2.vrm", "2D pose graph · 4 poses").

**Data flow**: `useCharacterPanel` fetches a persona's character_config (via `GET /personas/{id}`) the first time that persona appears while a surface is showing (`inlineVisible || windowOpen`), again when it starts speaking, and again when the editor saves → `parseCharacterConfig` → `useCharacterStore.setPersona` (kept by identity when the fingerprint, name and avatar are unchanged) + `activePersonaId`. `useCharacterBridgeSync` mirrors the store and the feed to the window; `CharacterWindowApp` writes what arrives into its own store and renders them through `CharacterStack` — one `CharacterSurface` per persona, bar the VRM personas waiting for the one live stage; a pose-graph surface's `PoseGraphDriver` calls `compositor.loadPoseTree()` to load all poses + initialize edge timers, and its frame loop hands the compositor the sampled amplitude, thinking, gestures and faces each frame.

**Graph editor (CharacterConfigDialog)**: reached from Settings → Personas → a persona → "Edit character graph"; it takes a `persona` and keys every asset path by that persona's id. React Flow (@xyflow/react) canvas with custom `poseNode` nodes. Nodes represent poses; one edge per directed node pair containing multiple transitions. Connecting an existing pair opens the edge editor instead of creating a duplicate. Sub-dialogs: PoseNodeEditor (3-step stepper for base/patches/preview), EdgeEditor (multi-transition cards with per-transition condition/video/playback rate). Right-click node for context menu (Toggle Default, Edit, Delete). Multiple nodes can be marked as default (`default_pose_ids: string[]`); one chosen randomly at runtime. Conversion: poseTreeToReactFlow/reactFlowToPoseTree. Video upload naming: `${edge.id}_t${transitionIdx}_${videoIdx}`. Each debounced auto-save also fires a `character-config-saved` window event carrying `{ personaId }` — `useCharacterPanel` listens for exactly that key to re-fetch the pose tree, so renaming it silently stops the live character window from picking up edits.

**3D setup editor (VrmSetupDialog, #242)**: reached from Settings → Personas → a persona → the 3D model card → "Set up 3D character". The kind cards above it only `PATCH {kind}` — no confirm, nothing removed. The editor is five steps and an optional Fine-tune, built for people who have never animated anything; none of its words is stored. A *move preset* (Still, Calm, Natural, Lively — `MOVE_PRESETS` in `@kurisu/models` `vrmSetup.ts`) is only a set of idle values, and `derivePreset` reads them back, so a number changed under Fine-tune shows as "Custom". A *reaction recipe* (`REACTION_RECIPES`: waves back, hand to chin while thinking, smiles when a face appears, nods at a thumbs up, brightens at a peace sign) is an ordinary `VrmReaction` whose `id` is the recipe's (`wave`, `think`, `greet`, `thumbs`, `peace`); on means present, and hand-written reactions are never touched. `greet` uses a `face` condition naming `*` — any face — which only the VRM reaction table understands. **Built-in moves** (`VrmMotion`: wave, nod, think, bow, stretch, look_around) need no clip: `@kurisu/vrm` `motions.ts` poses the normalised rig over the idle pose with an ease-in/out envelope, on the bones no clip is animating; a reaction can play one (`play: {type: 'motion'}`), and `idle.idle_motions` puts them in the idle rotation beside the idle clips — one pool, a pick every `idle_clip_interval_ms`, never while speaking or thinking. An absent `idle_motions` means none, and the server adds no moves or reactions of its own (a `vrm` body replaces the whole member, so a sub-member left out resets to its default); the editor writes its starting character — Natural with `['stretch', 'look_around']`, the wave/think/greet recipes on — as soon as it opens on a persona with no `vrm` member. In the idle rotation each pick plays once, a move or a clip on the one-shot slot, and the quiet wait runs only while nothing plays; a move replacing one under way hands its pose over in 250 ms instead of snapping. Choices autosave (`useDebouncedAutosave`, 800 ms) as `{kind, vrm}` without `model` and `clips`, which are the server's; an upload's response is folded in at once. Deleting one of her own animations first unnames it (idle list, clip reactions) and saves, because the server refuses to delete a clip something still names — and stops there if that save fails. A failed save keeps its value for the next attempt; Done closes only once everything is saved, and otherwise asks whether to leave without saving. A cancelled upload is silent. The preview (`VrmPreview`) drives its own driver from the buttons — never the live feed — and reloads only for a new model or clip list; everything else goes through the driver's `configure`.

**Emotion channel** (#243, what arrives; #244, when it reaches the face): for a persona whose character is a VRM model with `vrm.emotion.enabled`, the backend asks the model to tag a sentence whose feeling changes, strips the tag, and forwards a *cue*. On the stream it is `emotion` / `emotion_at` on the `stream_chunk` whose `content` starts at that point (`@kurisu/api` `websocket.ts` `StreamChunkEvent`); in the history it is `Message.emotion_cues`, the whole list in order (`@kurisu/models` `EmotionCueRecord { emotion: VrmEmotion; at: number }` — the recorded cue; the `EmotionCue` a driver is fed carries a hold and a weight instead, see `characterDriver.ts`). `emotion` is one of the six VRM preset names; `at` is an offset into the accumulated assistant text of that LLM round in UTF-16 code units — `String.length`, so `accumulatedContent.slice(at)` is exact and an emoji before the tag counts two. A tool call starts a new round and a new message, and the offsets restart at 0. A streamed bubble still carries no `emotion_cues` (`useStreamingChat` builds the streamed `Message` from a fixed list of fields); only a conversation loaded from history has them.

**When a feeling reaches the face** (#244). Text streams seconds ahead of speech, so a cue is shown when the sentence carrying it is *spoken*, not when its chunk arrives. `useStreamingChat` hands every assistant chunk to a `StreamSpeechPlanner` (`@kurisu/hooks` `emotionTiming.ts`), which is the stream's whole speech side: it groups the text for the TTS queue exactly as the hook used to inline (complete sentences, at least ten words, narration stripped) and gives each group the cues inside it as fractions of the way through (`selectCuesForSegment`, measured on the raw text before joining and stripping change lengths, since the offsets are into the text the backend counted). `useTTS.queueText(text, voice, cues)` keeps them on the queue item, and `segmentOf` turns each fraction into a `delayMs` into that sentence's `SpeechSegment` once its duration is known — including the silent 4 s hold of a sentence that could not be synthesized. The surface's frame loop hands the driver each cue once, when the audio position it already clocks passes the delay (`takeSegmentCue`, `@kurisu/models` `segmentCues.ts`); a spoken cue holds until the next one or until the queue drains, when the driver lets it go to `vrm.emotion.default_expression`. **A tool call does not shift later feelings**: every new bubble (another speaker, a tool, the same persona after a tool) first speaks what the last one left unsaid as its own group, then counts from zero — before this the desktop kept a short first-round tail in the buffer across the tool call, and every second-round cue would have landed that many characters early. A group that narration swallows is not spoken, and the feeling in force carries into the next group that is. **With speech off** (`storage.getTTSAutoPlay()` false) a cue shows as its text arrives: debounced 300 ms with the last of a quick run winning, flushed at once at a bubble boundary or the end of the turn, held for `max(1500, words × 350)` ms of its sentence (the subtitle's reading-time formula), and pushed into the feed with `pushEmotion(cue, personaId)` — the feed's `emotion` ref, an `EmotionBurst` with a rising `seq` like the gestures, which a surface takes once, only if it names that surface's persona (`CharacterSurface`'s `personaId`), and only once the character has loaded, so a feeling that arrives mid-download is not dropped. **A reopened conversation rests on its last feeling**: `useCharacterPanel`, on a conversation change, pushes the last cue of the last assistant message (`restingCueOf`) held until speech next ends; scroll-back replays nothing. The editor's preview shows each of the six expressions on demand from its own buttons (#242). Lip sync itself stays amplitude-only: `POST /tts` returns a WAV with no timings or phonemes, so there is nothing else to drive the mouth with. The mock backend's `emotion` scenario carries cues on the chunks and in the history. Nothing here reaches the voice: the viXTTS `emo_audio` / `emo_alpha` / `use_emo_text` request fields and the "Emotion Controls" in Settings → TTS were removed in the same change — the backend's `POST /tts` never declared them at any revision (`backend/docs/tts.md`).
