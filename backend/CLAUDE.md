# CLAUDE.md

## Project Overview

KurisuAssistant is a voice-based AI assistant platform combining STT (faster-whisper), TTS (GPT-SoVITS/viXTTS), and LLM (Ollama). Microservices architecture with Docker Compose.

This is the `backend/` package of the KurisuAssistant monorepo (see the root `CLAUDE.md`). The desktop and Android clients live in `../clients/`. Run every command below from `backend/` — that is where `docker-compose.yml` lives. (`data/` is resolved from the package location, not the working directory: `core/paths.py`.)

- History — `history_list` / `history_read` (`kurisuassistant/tools/history.py`). Searching is **Recall** (#6): `recall_regex` (a case-insensitive POSIX regex) and `recall_semantic` (pgvector cosine distance) over one `passages` table of verbatim slices of every user/assistant message and every readable drive file, each quoted whole with its conversation, speaker, time and message id — or file path and page. `history_search` (an unindexed `ILIKE` truncating to 200 chars) is gone. Both tools are `built_in`, but **drive passages are gated on `drive_read`** (allowlisted and not policy-denied; `execute_tool` injects `_available_tools` for this). The current conversation's still-in-context messages are skipped. The embedding model is **server-wide** (`EMBEDDING_PROVIDER` / `EMBEDDING_MODEL`, default Ollama `bge-m3`, reached through its own `EMBEDDING_API_URL` or `EMBEDDING_API_KEY` — never the chat settings; an empty model or no endpoint = semantic off); `embedding` is a dimensionless `vector`, so no HNSW — exact per-account scan. Indexing runs on its own `index-worker` / `index-scanner` threads (never on `db-worker`): a conversation is chunked in one DB callable (atomic against `delete_from_message`), a drive file is re-indexed when `checksum` differs from `indexed_checksum` and stamped even when unreadable, secrets are never indexed by name, and embedding failures are split into transient (pause with backoff, rows untouched) and permanent (bisect to the row, bump `embed_attempts`). A changed model is swept and re-embedded at scanner start. See `docs/retrieval.md`.
- LLM Providers — Multi-provider support: Ollama (local), Google Gemini, NVIDIA NIM and Poe (cloud). `provider_type` lives on the user's `assistants` row and on each `sub_agents` row; per-user `gemini_api_key` / `nvidia_api_key` / `poe_api_key` are write-only. **The Ollama URL and the keys exist only on the account** (#293): there is no `LLM_API_URL` or server-wide `*_API_KEY`, a provider built without its URL or key raises `ProviderNotConfigured` (`models/llm/base.py`), which reaches the user as its fixed sentence — `PROVIDER_NOT_CONFIGURED` on the socket, `400` via `core/errors.internal_error` — and `GET /models` asks only the providers the account has set up. NVIDIA and Poe are thin subclasses of `models/llm/openai_compat.py` (the OpenAI chat-completions dialect: message conversion, SSE parsing, readable error messages). Poe's model catalogue is public, so `PoeProvider.validate_key` probes with a one-token request for a nonexistent model instead of listing models; every provider exposes `validate_key()`, which `POST /models/validate-key` calls. Provider factory in `kurisuassistant/models/llm/__init__.py`.
- Auth rate limiting — Two in-process buckets on `/login` and `/register`: per client address (10 per 5 min) and per username (20, `AUTH_RATE_LIMIT_MAX_ATTEMPTS_PER_USER`, `0` disables). The address is only as good as `FORWARDED_ALLOW_IPS`, which `docker-entrypoint.sh` turns into uvicorn's `--proxy-headers --forwarded-allow-ips`; unset means the header is ignored rather than trusted, and behind a proxy that means one bucket for everyone (#155). The username bucket is what survives a shared address or an attacker with many; it can also keep a named account refused for a window, which is the deliberate cost. Both refusals read the same.
- Authentication — JWT access (1h) + refresh (30d) tokens. Secret persisted to `data/jwt_secret.key`. Refresh endpoint: `POST /auth/refresh`. Client auto-refreshes on 401/4001 with exponential backoff WebSocket reconnection.
- Assistant / Persona / Sub-Agent Split — The merged `Agent` model is **gone**; migration `0dacee9f63b8_split_persona_from_assistant` reversed the earlier merge. Three tables now:
  - **`assistants`** — exactly one row per user, capability only: `model_name`, `provider_type`, `available_tools` (null = every tool), `think`, `use_deferred_tools`, `memory`, `memory_enabled`, plus `trigger_word` and `default_persona_id`. Created at registration (`core/accounts.py::provision_user`, which makes **no persona** — they are optional, #302), so `/assistant` has GET and PATCH but no POST and no DELETE. `model_name` is the one field provisioning **cannot** fill — which model to use depends on the operator's providers and there is nothing to ask at registration — so every new account starts with it NULL. A `chat_request` with no model on the row and none in the request is refused with an `error` coded `NO_MODEL_SELECTED`, checked inside `_setup_conversation` above `create_conversation` so nothing is created; both clients turn that code into a way onto the Assistant screen (#149).
  - **`personas`** — many per user, presentation only: `name`, `description`, `system_prompt`, `preferred_name`, `voice_reference`, `avatar_uuid`, `character_config`, `enabled`. A persona has **no model, no tools, no memory and no trigger word**.
  - **`sub_agents`** — task-only workers with their own `model_name`/`provider_type`/`available_tools`/`think`/`use_deferred_tools`, no identity and **no memory** (the consolidation pipeline only ever wrote main-agent memory, so the column could never have been filled).
  - The migration renames `agents` → `personas` **preserving ids**, because `data/character_assets/{id}/` and the URLs inside `character_config` are keyed on them. There is deliberately no disk work in it. `conversations.main_agent_id` → `conversations.persona_id`, `messages.agent_id` → `messages.persona_id`. The `/agents` REST surface is removed, not aliased.
- Agents & Orchestration — Two concrete agent classes in `agents/`:
  - **`MainAgent`** (`agents/main.py`) — constructed as `MainAgent(assistant, tool_registry, identity=persona)`. `capabilities` is an `AssistantConfig` (what it can do); `identity` is a `PersonaConfig` (who is speaking). Streams `StreamChunkEvent` to the user and owns the conversation.
  - **`SubAgent`** (`agents/sub.py`) — task-only, no identity, no streaming to frontend. Runs an internal LLM + tool-loop and returns a single string to its caller via `execute(task, context)`. Exposed to a MainAgent's LLM through the `SubAgentTool` adapter in the same file; `capabilities` and `identity` are the same `SubAgentConfig` object.
  - Both extend `BaseAgent` (`agents/base.py`) for shared tool-approval + MCP plumbing.
- Conversation = at most one persona — **A persona is optional (#302)**: with none, the assistant answers as itself (`selection.assistant_identity()`: no id, the name `Assistant`, no prompt/voice/character; the prompt opens `You are the user's personal assistant.`), and chunks carry `persona_id: null`. A new account has no persona and a null `default_persona_id`. Each `Conversation` has a nullable `persona_id` FK — null is the assistant. `agents/selection.py::pick_persona` resolves it deterministically: explicit override (`chat_request.persona_id`, or the stored binding) → `assistants.default_persona_id`, **only for a conversation nothing has answered yet** (so a chat with the assistant stays with it) → the assistant itself. There is no first-persona fallback and no `NO_PERSONAS`. Creating or importing a persona never makes it the default; deleting any persona (the last included) or disabling the default hands new chats back to the assistant. **There is no trigger-word scan and no random pick.** The trigger word is an assistant-level *voice wake word*: saying it wakes the assistant and the bound persona answers; it selects nothing. A persona override is written back to `conversations.persona_id` on every rebind (also settable out of band with `PATCH /conversations/{id}`, where `null` hands it to the assistant), so it survives a reconnect.
- Frames removed — The old `frames` table + `message.frame_id` + `Frame.summary` are gone (migration `0caebafdf4cc`). Messages are stored directly on the conversation (`message.conversation_id` indexed FK). `Conversation.compacted_context` is the sole summary source.
- Rolling Context Compaction — At 90% of the model's context window the conversation is compacted **in place**: an inline LLM call produces a ~10% summary, `_compact_in_place` writes it to `conversations.compacted_context` and moves `compacted_up_to_id` to the last message it covers, and `_load_context_messages` reads the summary plus everything after that id. The conversation keeps its id, title, persona binding and stored messages. `context_info` is sent with `compacting: true` and again with `compacting: false` on **every** exit path — the empty-summary path used to return leaving the client's spinner running. Compaction used to fork into a new conversation and emit `conversation_switched`; that event no longer exists (#99). Manual trigger: the `compact_context` WebSocket event.
- Context accounting — `utils/tokens.py` estimates what a message list costs: characters over words, plus per-message framing, thinking blocks, tool-call arguments, and a flat `TOKENS_PER_IMAGE` per image (never the length of a UUID or of base64). It drives both the compaction trigger and the counter on `stream_chunk`, so the two cannot disagree. It is still an estimate biased high — no provider here reports its own prompt token count back to the handler (#99).
- Memory Consolidation — Memory is **one document per user**, on that user's single `assistants` row, shared by every persona. Runs at **conversation idle**: `_scan_idle_conversations()` (`workers/service.py`, every 60s) finds conversations whose `updated_at` is past `CONVERSATION_IDLE_THRESHOLD_MINUTES` whose owner's assistant has `memory_enabled = true` and which have at least one message, and which have not been consolidated since they last changed (`conversations.consolidated_at` null or older than `updated_at`), oldest first, at most `SCAN_LIMIT` (50) per scan over an index on `updated_at`, and enqueues **one** `ConsolidateMemoryTask` per conversation (no agent id — the target is derived from `user_id`). The outcome is written back to the row (#96): success stamps `consolidated_at`; a failure — `consolidate_assistant_memory` now **raises** instead of swallowing — bumps `consolidation_attempts` and sets `consolidation_next_retry_at` (5 min doubling, 6 h cap), and after `MAX_ATTEMPTS` (5) the row is stamped and left alone until it changes. The in-memory `_queued` set only covers the in-flight window and is released in a `finally`. `utils/memory_consolidation.py` feeds the bound persona's `system_prompt` in as "session instructions" but the document itself must stay persona-neutral. **The read-modify-write on `assistants.memory` is only safe because the single `db-worker` thread serializes it** — do not parallelize it without making the write atomic. Empty LLM output is **logged**, not silently dropped.
- Message Queue — `_message_queue` on `ChatSessionHandler` queues incoming `chat_request` events while the agent is busy instead of cancelling the running task, capped at `MAX_QUEUED_MESSAGES` (20); over the cap the client gets an `error` with code `QUEUE_FULL`. `_process_queue()` merges the queue into one follow-up turn after `done` or an error — except `NO_MODEL_SELECTED` and `PROVIDER_NOT_CONFIGURED`, which **clear** it instead: every queued message would fail the same way, and replaying them at the end of the next turn would answer them after the user had picked a model, long after they were sent (#149). `_handle_cancel` clears the queue too.
- Tool Approval — **The server is the policy authority.** `users.tool_policies` is read once per turn onto `AgentContext`, and `BaseAgent.execute_tool` applies it before dispatch: a stored `deny` returns immediately and never reaches the client; a stored `allow` skips the prompt; anything else emits `ToolApprovalRequestEvent` (with `execution_location` = "backend" or "frontend") and the client's answer can only narrow the server's decision, never widen it. With no client session attached, an unapproved call is refused rather than run. Policies are managed via `GET/PUT/PATCH /users/me/tool-policies`. Per-tool `requires_approval` / `risk_level` flags do not exist.
- Speech is wrapped here, synthesized elsewhere — `kurisuassistant/speech/` (#212, #227) is the whole of speech in this project. **Every synthesis engine speaks one contract** — `docs/speech-engine-contract.md`: health with `loaded`, voices, a multipart synthesize with the clip uploaded, release, an idle timeout — so `engines/standard.py` is the one adapter for all of them, and an engine is configured by one `name=url` entry in `TTS_ENGINES`; the names are the model ids the clients store. Recognition (`engines/whisper.py`) keeps its own dialect and `ASR_URL`. `text.py` cuts 200-character chunks and wraps raw PCM; `synthesis.py` and `recognition.py` make one call each. **Nothing here imports torch, loads a model, reads the GPU or touches a container.** An engine not listed is a 502 naming the profile to start, never a silent empty list (#151); a 400 — a model this server does not run, a language the engine refuses, no clip for an engine that only clones — keeps its status and reason; anything else is 502 "The speech service is unavailable." with a log reference. A refused chunk is skipped when others speak; `merge_wav_files` parses even a lone chunk, so a proxy's error page with a 200 becomes the outage sentence rather than an unplayable file. **Residency is the engines' own.** Each drops its weights after `IDLE_TIMEOUT` and on `POST /release`, refuses release with 409 while a synthesis is in flight, and answers **503 when it cannot load** — the memory-pressure signal. `synthesis.py` answers that by releasing the least recently used other engine (`_last_used`, the only state it keeps) and trying once more; the residency scheduler, the Docker socket proxy and the GPU read in the API (#221, #223) are gone. The clients know nothing: audio, or the failure sentence they already handle. GPT-SoVITS speaks the contract through `kurisu_engine.py` in the owner's fork (it hosts `api_v2` as a child and ends it to give memory back; ~35s cold to first audio), viXTTS natively in its own server (~20s). `tests/test_tts_router.py` pins the dialect and the release-and-retry.
- Failures are loud — Three things used to fail silently and now do not. The single `db-service` thread logs every failed operation with a traceback, waits at most `DB_OPERATION_TIMEOUT_SECONDS` before raising `DBUnavailableError` (a 503 via `core/errors.py`), and the engine has connect and statement timeouts (#153, `docs/database.md`). Provider `list_models()` **raises** on an unreachable host — never an empty list, never a fabricated catalogue — and `GET /models` reports each unreachable provider in `unavailable`, or 502 when none answered; `GET /tts/models` is 502 when no synthesis engine is configured (#151). Gesture detection resolves its torch device (`VISION_DEVICE`, else `cuda` if available, else `cpu`) instead of assuming a GPU (#152, `docs/vision.md`).
- Image Storage & Access — Two directories under `data/image_storage/data/`: each user's own `users/{user_id}/`, and a **flat legacy store** at the top level. `upload_image()` writes into the uploader's directory (since #154), so an image has an owner from the moment it exists — which is what lets the persona editor preview an avatar that no row references yet. The flat store is read-only history: avatars and face photos written before that. **Neither GET route is public.** Both `GET /images/{uuid}` and `GET /images/u/{uuid}` authenticate by header *or* `?token=` (an `<img src>` cannot set a header) and serve `Cache-Control: private`. `/images/{uuid}` serves an image from the caller's directory outright, and one from the flat store only if a row the caller owns references it (`users.agent_avatar_uuid`, `personas.avatar_uuid`, `face_photos.photo_uuid` via `face_identities`); anything else is **404, never 403**, so the response cannot confirm a UUID exists. It was public until #154 — the docstring said "Serve image publicly" — which exposed every avatar and face photo to anyone who could reach the port. **The attach is guarded too**, in `routers/personas.py`: `avatar_uuid` is a client-supplied string, so a read-side check alone would be self-serving — attach a UUID you overheard to your own persona and the row makes it yours. `core/image_access.py` holds the one predicate both ends use. The desktop client puts the token on the URL; Android needs nothing, because its Coil loader is built on the authenticated OkHttpClient (`KurisuApplication`).
- Wire Protocol — `version.py` holds `WIRE_PROTOCOL`, currently **7**, with a full changelog. `__version__` is not committed (#291): it is resolved from `KURISU_VERSION`, stamped into the image at build time from `git describe --tags` (a plain X.Y.Z is a release; anything else, or `dev`, is not), and `release.yml` asks `version.py <tag>` whether a tag may be released. HTTP requests carrying a mismatched `X-Wire-Protocol` get 426 (`/health` and `/version` exempt). The `/ws/chat` handshake enforces the same number — header, or a `kurisu.wire.<n>` subprotocol entry for browsers — and closes with **4426** *before* authenticating. Absence is allowed on both transports.
- Character store — `data/character_assets/{persona_id}/` is served and filled by `routers/character.py`, but **what a saved `character_config` may delete is decided in `kurisuassistant/character/`**: `paths` owns the root (`CHAR_ASSETS_DIR`, read at call time so a test patches one name, no import-time mkdir) and `safe_segment`; `references.classify` is fail-closed — `refs: None` for a body it cannot classify or one pointing at another persona's ids (and a `refusal` naming the member and the cause, which becomes the 422 detail), and the sweep deletes nothing on `None`; `config_write` is the one path both writers (`PATCH /character-assets/{id}/character-config`, `PATCH`/`POST /personas`) go through: merge the body over the stored row member by member (`kind` replaced; `pose_tree`/`vrm` kept when absent, cleared when `null`; `vrm.model`/`vrm.clips` server-owned) → validate through `schema.py` and classify → 422 before anything is written, write, then sweep in a thread — and the sweep never fails a committed save (a vanished file or a directory an upload just filled is logged, not a 500). It used to sweep before the write and treat an unknown shape as "references nothing", which emptied the directory (#233); "cannot classify" is strict — a list or string where a member wants an object, a non-object node or patch, a non-string URL, is `None`, never an empty tree (a `null` member, with a `kind`, is a deliberate clear). `.incoming/` and symlinks are never walked. `DELETE /personas/{id}` removes the persona's whole directory after the row is gone, and `scripts/sweep_character_assets.py` (dry run by default) finds directories no persona owns any more (#234). **Every config carries a `kind`** — `pose_graph` or `vrm` — required on the wire since protocol 7 and stamped onto existing rows by migration `3eb07d0e8d1f` (#235); the two members coexist so switching back needs no upload, and the walker reads both whichever is selected. **The VRM model and clips (#236)** stream in as raw bodies (`?sha256=` required) to `{id}/vrm/{sha256}.vrm` (content-addressed: placed before its ref commits, the old file removed after, the file served being the one the stored ref's sha names — so bytes and `ETag` cannot disagree) and `{id}/vrma/{clip_id}.vrma`, validated from the glTF header and a bounded JSON chunk parsed off the loop (`character/assets.py`: `415` with a `code` — `not_glb`, `not_vrm`, `no_humanoid`, `not_vrma`, `bad_json`), and their refs are written into `vrm.model`/`vrm.clips` in the transaction that accepts the bytes; the account quota (`CHARACTER_ASSETS_QUOTA_BYTES`, 1 GiB; per file `CHARACTER_MODEL_MAX_BYTES` 100 MiB, `CHARACTER_CLIP_MAX_BYTES` 16 MiB) is the sum of the stored refs, measured again inside that transaction; the GETs serve an `ETag` from the stored sha with `304` and `nosniff`. **A persona export can carry its character (#248):** `GET /personas/{id}/export?character=true` is a v4 zip bundle (`character/bundle.py`) — `persona.json` with the config's URLs against a `{persona_id}` placeholder plus a sha256 manifest, and the referenced files under `character/` (a referenced file missing on disk fails the export with a 500 and an error log, never a bundle without it); `…/export/size` reports it first; `POST /personas/import/bundle` streams one in (raw body, no size ceiling of its own — its own nginx location with none —, `PERSONA_BUNDLE_MAX_FILES` bounding its directory), checks every file against the manifest, the store's own layout and its kind's ceiling, re-inspects the model and clips and rebuilds their refs from the bytes, plans the config through `config_write` with those refs as the stored ones (so a foreign URL is a 422), meters the VRM bytes against the quota in the transaction that creates the persona, and only then moves the files in under the new persona's lock; the plain JSON export is unchanged. Every "commit, then touch the disk" pair — uploads, their deletes, a config save and its sweep, a persona delete — holds `character/locks.persona_lock`, so a sweep planned before an upload's commit cannot remove the file that upload places (in-process: one uvicorn worker). Route detail in `docs/API.md` (Character Assets).
- Emotion channel — A VRM persona's face needs the persona's feeling, and the persona says so in its reply (#243): when `character_config` is `kind: vrm` with `vrm.emotion.enabled`, `MainAgent._prepare_messages` adds an `## Expression` block asking the model to open a sentence with `[[emotion:happy]]` (the six VRM presets) when its feeling changes, and the loop runs each round's text through an `EmotionSource` (`character/emotion_source.py`; today `character/emotion_tags.py::EmotionTagStripper`, one per LLM round) that strips the tags and reports where they stood. A cue leaves as `emotion` / `emotion_at` on the `stream_chunk` whose content starts there — offsets in **UTF-16 code units** into the round's clean text, the unit both clients count in — and is stored per assistant message in `messages.emotion_cues`, served by the history. `message` and `raw_output` are the stripped text; nothing else on the server reads a cue. No prompt, no stripper, and a byte-identical stream for any other persona. The same two methods with a classifier behind them is #247. `docs/agents.md` "The emotion channel".
- Kurisu Drive — Account-scoped file storage (#17), REST only: `routers/drive.py` over `drive_nodes` and `data/drive/{user_id}/{storage_key}`. **Everything is addressed by node id, not by path** — the one route that takes a path walks it segment by segment against rows, and blob paths are built only from a server-generated UUID, so traversal is not something to sanitise but something that cannot be expressed. That is the deliberate opposite of `routers/character.py` and `routers/tts.py`, which join request parameters onto real paths (the character router now refuses any segment that is not one plain name, #233). It gives back **the bytes it was given** — six of the other upload routes decode and re-write theirs (`utils/images.py` at JPEG quality 90, `routers/character.py`'s pose art as PNG); `POST /character-assets/upload-video` already stored video verbatim, but only video, and only against a persona id. It **streams** — `utils/drive_storage.store_stream` writes incrementally to `.incoming/` over the shared `utils/blob_stream.write_stream` and enforces `DRIVE_MAX_FILE_BYTES` (413) and `DRIVE_QUOTA_BYTES` (507) as the bytes arrive; the character store's VRM uploads are the only other routes that do, and the remaining `UploadFile` routes read the whole body first (the pose-graph three bounded to their ceiling). Downloads go through `FileResponse` (so `Range`/206 is free) as an `attachment` with `nosniff`, and `?inline=1` is honoured only for types that cannot execute — never `text/html`, never `image/svg+xml`. A node that is not yours is **404, never 403**. Deletion is hard, rows before blobs. Four non-`built_in` tools (`drive_list`/`drive_read`/`drive_write`/`drive_delete`) go through the same repository, and the three-way Settings policy is a *view over* `users.tool_policies`, not a second column. Every written file is queued for the retrieval index (Recall, above). See `docs/drive.md`.
- Vision transport — A webcam frame is a WebSocket **binary** message (`websocket/binary.py`: `[version][type][header length][JSON header][JPEG]`), not a JSON event. It was base64 inside JSON on the chat socket, which delayed the assistant's next token behind the pixels, inflated every frame by a third, and cost a JSON parse per frame (#111, protocol 6). `vision_start`/`vision_stop` are still JSON. A bad binary message answers `BAD_BINARY_MESSAGE` and keeps the socket.

## Alembic Migrations

- **Always** use `cd kurisuassistant/db && alembic revision --autogenerate -m "short_snake_case"` — never hand-write migration files.
- Naming: `-m` becomes the filename slug. Use `add_foo_to_bar`, `remove_baz_column`, `create_widgets_table`.
- After generating, verify single head: `cd kurisuassistant/db && alembic heads`. If multiple heads, merge with `alembic merge heads -m "merge_heads"`.
- **Declare every index on the model, including ones written in raw SQL.** An index a migration creates but the model does not declare is invisible to autogenerate, which then proposes dropping it on every run — and a deployment can silently end up without it while its migration history says otherwise (#162). `tests/test_schema_matches_models.py` runs `compare_metadata` against a freshly migrated database and fails when the two disagree.
- Review the generated `upgrade()`/`downgrade()` — autogenerate misses renames and data migrations.
- Never use plain-text revision IDs — always let Alembic generate the hash.
